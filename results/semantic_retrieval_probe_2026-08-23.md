# 語義向量檢索可行性量測（離線原型，未動 VM）

2026-08-23。`scripts/semantic_retrieval_probe.py`，BGE-small-zh-v1.5
（Mac 端 `.venv-emb`，Intel Mac 限定 torch 2.2.2＋transformers 4.44 手動
CLS pooling；VM 零改動）。方法：17,071 筆 gloss_clean 嵌入向量；句子側
整句＋2–4 字 n-gram 當查詢、取每 gloss 最高相似度；排除既有 k=60 候選後
取前 M 名額，量「檢索沒撈到但庫裡有」的參考 token 回收率。

## 結果

| | dev（484 miss） | test_corpus（337 miss） |
|---|---|---|
| +10 名額 | 10.3% | 11.9% |
| +20 名額 | 15.3% | 16.6% |
| +40 名額 | 21.3% | 20.8% |

換算詞涵蓋率（在 k=60 基礎上加 40 個語義名額）：
dev 82.5→約 86.1%（+3.6pp）、test_corpus 72.5→約 78.1%（+5.6pp）。

**回收的確實是語義距離遠的那類**：學到了→學習、幼稚園→幼兒園、
作畫→繪畫、年齡→年紀、很多人→人多、辦畫展→辦展覽——
字面比對撈不到、語義向量撈得到，機制符合預期。

## 但三件事必須一起講

1. **即使給 40 個名額，79% 的缺口仍在。** 剩下的多半不是「同義詞距離」
   問題而是結構問題：上下文帶入的詞（前句話題）、空間指示、
   聾人慣用壓縮——任何以單句中文為輸入的檢索都拿不到。
   語義檢索能把天花板抬高 5pp 上下，不能捅破。
2. **+40 名額等於 k≈100，v15 剛付過學費。** k 40→60（+20 個干擾項）
   就讓約束違反率近乎翻倍、品質沒漲。直接疊 40 個語義候選重蹈覆轍的
   風險很高；比較合理的設計是**同 k=60 預算內換血**——砍掉最弱通道
   （字元重疊干擾項）騰名額給語義通道，這需要一輪控制變因實驗。
3. **實驗全程不需要動 VM。** 候選建置（`build_script_dataset.py`）在
   Mac 跑，訓練與推論只讀建好的 jsonl——語義通道的訓練實驗
   **零 VM 依賴**。「共用機可否裝依賴」只在**要上線部署**時才需要問：
   線上服務的檢索器必須與訓練同分布，屆時要嘛裝 BGE（獨立 venv、
   模型 ~100MB、CPU 毫秒級），要嘛用已載入的 Gemma 抽 hidden state
   （零新依賴的備案，品質未驗）。

## 建議

- 值得做的下一步：**同預算換血實驗**（k=60 內以語義通道取代字元重疊
  通道），Mac 上建資料、照 v15 流程訓一輪。預期 test_corpus 涵蓋率
  +3~5pp 而不增加候選數（干擾項不變多）。
- 問「裝依賴」這件事可以**延後到實驗證明有效之後**——拿著實驗數字去問，
  比拿著可行性數字去問有力，而且若實驗失敗就根本不用問。
- 誠實邊界：本量測是回收率上限估計（n-gram 查詢與實際通道實作可能有
  出入）；涵蓋率 +5pp 不代表品質 +5pp（v15 的教訓）。

# v21 報告：min-coverage 豁免「整詞缺」沒有修好拆字（2026-09-09）

v21 = v19 的資料 + 39 列。那 39 列是 `--min-coverage 0.8` 新預設（豁免「整詞不在庫、
但每個字都在」的 OOV，commit `f9692ed`）救回來的，教「不要拆字、把整詞列進
oov_items」的例子由 19 列回到 58 列（`whole_word_gap_rows`）。其餘完全相同：
k=60、LOGO、min-coverage 0.8、schema V3、無前文；dev／test／test_corpus／test_textbook
與 v19 **逐位元相同**，prompt 形狀也相同（`56a8d9b` 修掉了 context 鍵的差異）。
train 5,545→5,584，v19 的每一列都原樣在 v21 裡。

checkpoint-349（epoch 1，依既定規則；eval_loss ep1 **0.1951** / ep2 0.2467，v19 是
0.1872 / 0.2502），訓練 137 分鐘、峰值 11.5 GB。門檻 0.001814（dev max-F1 0.7642）。
manifest 確認推論用 `splits_script_v21`、約束解碼開啟、commit `1fedad1`。

## 一句話

**人工盲測 88 題 v21 勝 69%（p=0.004），語意 +0.40，漏詞備註 19→4——v21 比 v19 好，建議部署。**
但它好的原因**不是**這次要修的拆字：拆字零改善、OOV 旗標反而變弱（第一～五節，
盲測回收前寫的分析，全部成立）；它好在**漏詞更少**，而那多半是同 seed 下資料微變
帶來的訓練軌跡差異，不是那 39 列的功勞。第六節是盲測結果。

## 四、為什麼沒效

1. **候選主訊號壓倒一切**。5,584 列裡「從候選挑字」是壓倒性的模式；只要候選裡有
   單字，模型就挑。依較寬的定義（整詞缺且候選有 ≥2 單字），v19 的 train 本來就有
   178 列這種例子、v21 有 198 列——v19 有 178 列還是拆字，多 20 列不會改變什麼。
2. **例子的型態不對**。救回的 39 列，整詞缺是語料庫式的複合 gloss：回家、她們兩個、
   叫人起床、他們倆人、送我。模型從中學到的是「語料庫這種寫法算 OOV」，
   與專有名詞（毛利人、調香師）不是同一種東西。
3. **批間變異可能大於這 39 列**。eval_loss 0.195 vs 0.187、旗標 true 率下降 6–15 個
   百分點，這不像 0.7% 的資料能造成的方向性變化，比較像是同 seed 下資料微變
   導致的訓練軌跡差異——v18→v19 的輸出長度也曾這樣大幅擺動。

## 五、結論與建議

| 問題 | 答案 |
|---|---|
| 豁免救回的 39 列有沒有修好拆字 | **沒有**——正解 10→0，拆字 19%→17%，五句全數仍拆 |
| 自動指標的小升可信嗎 | 不能單獨採信；盲測決定 |
| v21 該上線嗎 | 自動指標不足以決定；**盲測回收後：該**（見第六節） |
| 豁免要不要留 | 留作預設——它的語意是對的（那些句子不是爛句），也沒傷指標；但別再期待它修拆字 |
| 拆字到底怎麼修 | 在候選層：整詞缺時把單字候選壓掉（decode-time 版曾因 43% 誤判否決，需更嚴的觸發條件），或補片——`data/video/補片_整詞缺但單字都有.csv` 129 詞請手語老師先判定哪些是單一手語 |

（以上一～五節寫於盲測回收前。）
